# Гайд по архитектуре проекта

Этот документ описывает архитектуру проекта на уровне решений и модулей. Его цель - зафиксировать не конкретную реализацию на Nuxt/Vue, а переносимую схему, которую можно повторить на другом frontend-фреймворке.

## 1. Общая идея

Проект построен как frontend-приложение для интернет-магазина, где основным источником данных остается WordPress/WooCommerce backend. Frontend отвечает за маршрутизацию, отображение страниц, клиентские состояния, локализацию интерфейса, формы, SEO-метаданные и UX-модули.

Ключевой принцип: компоненты сайта не обращаются к WordPress напрямую. Между интерфейсом и backend есть серверная API-прослойка приложения. Она скрывает адрес backend, формат запросов и технические детали интеграции.

Высокоуровневый поток:

```text
Пользователь
  -> Страница frontend-приложения
  -> Локальный server/api endpoint
  -> Общий API-клиент backend
  -> WordPress/WooCommerce REST API
  -> Данные возвращаются в страницу
  -> Страница передает данные layout/ui-компонентам
```

Такую схему можно повторить в любом фреймворке: Next.js, Remix, Astro, SvelteKit, Laravel + Inertia, обычный SPA с отдельным BFF-сервером и т.д.

## 2. Основные слои

### 2.1. Backend-слой

Роль: хранение и выдача бизнес-данных.

В текущем проекте эту роль выполняет WordPress/WooCommerce с кастомными REST endpoint-ами вида:

```text
https://site.com/wp-json/api/*
```

Полный справочник эндпоинтов (параметры, ответы, ошибки, кеш, константы `wp-config.php`): [docs/wp-api.md](docs/wp-api.md).

На backend хранятся:

- страницы CMS;
- товары;
- категории и бренды;
- меню;
- переводы контентных страниц и URL;
- SEO-данные;
- хлебные крошки;
- отзывы;
- заказы;
- данные для фильтров и сайдбаров.

Frontend не дублирует эти данные как постоянное хранилище. Он только запрашивает их, кеширует там, где это оправдано, и отображает.

### 2.2. Server API / BFF-прослойка

Роль: единая точка общения frontend с backend.

В проекте этот слой находится в:

```text
server/api/
server/utils/wpFetch.ts
```

`wpFetch` - общий backend-клиент. Он берет адрес WordPress из `runtimeConfig.wpSiteUrl` (только сервер, в браузер не попадает), добавляет REST-префикс и таймаут. Ошибки WP он превращает в ошибки с тем же смыслом: 404 остается 404, прочие 4xx уходят клиенту вместе с `data` (например, ошибки полей заказа 422), а сбой сети, таймаут и 5xx превращаются в 503.

Endpoint-ы в `server/api/` сгруппированы по предметным областям:

- `route` - что лежит по пути: тип объекта, canonical, переводы (alternates), SEO и крошки Yoast;
- `menus` - header, footer и mobile menu одним запросом;
- `archive` - товары каталога, фильтры, сайдбар;
- `product` - страница товара, новый отзыв;
- `home` - данные главной страницы;
- `page` - CMS-страницы;
- `reviews` - все отзывы;
- `search` - поиск;
- `cart` - котировка корзины (цены, наличие, купон), создание заказа, данные заказа по ключу;
- `subscribe` - форма подписки (прокси к legacy AJAX темы);
- `_revalidate` - вебхук WP для очистки кеша Nitro.

Чтения идут через GET и кешируются Nitro, записи — через POST. Endpoint передает в WP только известные параметры (`lang` — только `ru`/`uk`), чтобы мусор из запроса не плодил записи кеша. Для заказов и отзывов BFF передает IP покупателя в `X-Branded-Client-IP` с секретом `X-Branded-Secret`, иначе лимиты WP посчитали бы всех покупателей одним IP сервера.

Кроме endpoint-ов, в `server/middleware/` есть два обработчика:

- `01.redirects.ts` - 301 на вариант со слешем, `/…/page/N/` → `?page=N`, старый поиск `/?s=` → `/search/?s=`, личный кабинет WooCommerce (`/my-account/…`, `/uk/mij-akaunt/…`) → главная языка (кабинета на фронте нет);
- `02.wp-files.ts` - проксирует карты сайта Yoast (`sitemap_index.xml`, `*-sitemap.xml`).

Задача этого слоя - не рисовать UI и не хранить состояние, а быть адаптером между frontend и внешним backend. Если backend изменится, в идеале меняется только этот слой и контракты данных, а страницы и компоненты остаются максимально стабильными.

### 2.3. Страницы и маршруты

Роль: собрать данные для конкретного URL и передать их ниже.

В проекте страницы находятся в:

```text
app/pages/
```

Основные типы страниц:

- главная страница (`index.vue`);
- страница товара (`product/[productName].vue`);
- архивы: категории (`product-category/[...slug].vue`), бренды (`brand/[brandName].vue`), сезоны (`sezon/[...slug].vue`) — тонкие обертки над `LayoutLArchivePage`;
- catch-all (`[...page].vue`) — все остальное: CMS-страницы, архивы прочих таксономий (`/бренд/…`, `/color/…`), а также WP-страницы с особой версткой, которые определяются по `default_id` из `api/route` (ID в языке по умолчанию, слаги в языках разные): 540 «Отзывы» (`/reviews/`, `/uk/vidguky/`), 27 «Sales». WP-копии корзины и checkout (7318, 7319) отдают 301 на маршруты фронта, личный кабинет (7320) — на главную;
- поиск, корзина, checkout, страница успешного заказа — маршруты фронта без объекта в WP.

Страница с объектом в WP делает параллельно два запроса:

- `api/route` по своему пути — SEO, крошки, переводы, `redirect`;
- свои данные (товар, товары архива, контент страницы).

Затем она вызывает `guardPageRoute()`: ошибка 404 от WP дает 404, любая другая ошибка — 503 (сбой WP не должен выкидывать страницы из индекса), `redirect` дает 301. После этого `usePageSeo()` собирает `<head>`.

После загрузки страница не должна содержать слишком много UI-логики. Ее основная задача - быть маршрутизатором данных: получить данные, обработать базовые состояния загрузки/ошибки и передать результат компонентам.

### 2.4. Layout-компоненты

Роль: крупные блоки интерфейса, которые знают о структуре конкретной части сайта.

Папка:

```text
app/components/layout/
```

Примеры:

- header;
- footer;
- корзина;
- мини-корзина;
- сайдбар;
- блок фильтров;
- блоки главной страницы;
- похожие товары;
- модальное окно;
- форма checkout-раскладки.

Layout-компоненты могут быть достаточно умными, если это делает их переиспользуемыми. `LArchivePage` сам загружает товары, сайдбар и (если не передан) `api/route`, выставляет SEO и обрабатывает фильтры — им пользуются все архивы и catch-all. `LReviewsPage` так же устроен для страницы отзывов. Сайдбар и хлебные крошки, наоборот, только отображают готовые данные от страницы.

### 2.5. UI-компоненты

Роль: маленькие переиспользуемые элементы интерфейса.

Папка:

```text
app/components/ui/
```

Примеры:

- кнопка;
- меню;
- переключатель языка;
- карточка товара;
- список товаров;
- хлебные крошки;
- аккордеон;
- спиннер;
- page loader;
- search form;
- logo.

UI-компоненты должны быть как можно более независимыми от источников данных. Лучше передавать им готовые props и события, чем заставлять каждый UI-компонент знать, откуда пришли данные.

### 2.6. Composables / сервисные хуки

Роль: общая логика, которую используют страницы и компоненты.

Папка:

```text
app/composables/
```

Ключевые composables:

- `usePageRoute` - `useCurrentPath`, `useCurrentPage`, `useRouteData` (запрос `api/route`), `guardPageRoute` / `throwPageError` (404/503/301), `usePageAlternates` (переводы страниц для переключателя языка);
- `useSeo` - `usePageSeo` собирает `<head>` из `api/route`: мета Yoast, hreflang, canonical на домене `siteUrl`, prev/next, граф schema; `useServicePageHead` — заголовок и noindex служебных страниц;
- `useMenus` - все меню одним запросом, общий для шапки и подвала;
- `useSiteLinks` - пути WP-страниц, на которые ссылается верстка, в обоих языках (`/reviews/` ↔ `/uk/vidguky/`);
- `useProductVariation` - выбор вариации по всем атрибутам (размер, цвет…) на странице товара, как форма вариаций WooCommerce;
- `useCartQuote` и `useCartSummary` - котировка корзины в WP, купон, строки итогов;
- `useOrderForm` - форма заказа для checkout и «Купить в 1 клик»: поля, валидация, отправка, ошибки WP;
- `useAnalytics` - GA4-события в dataLayer в формате темы WP;
- `usePopup` - управляет глобальными попапами;
- `useWaitRequest` - защищает формы и действия от повторного запроса;
- `useLanguageSwitchLoader` - хранит состояние загрузки при переключении языка;
- `usePerfMonitor` - состояние клиентского монитора производительности.

Типы ответов API лежат в `app/types/wp-api.ts`.

Идея для переноса: всю повторяемую бизнес- или UX-логику выносить в отдельный сервисный слой, а не размазывать ее по компонентам.

### 2.7. Plugins

Роль: подключить глобальное поведение приложения.

Папка:

```text
app/plugins/
```

Основные плагины:

- popup plugin - закрывает попапы при смене маршрута и предоставляет глобальный доступ к popup API;
- language switch loader plugin - останавливает loader после завершения страницы или ошибки;
- cart plugin - после полной гидрации (`onNuxtReady`) переносит корзину из `localStorage` в store;
- analytics plugin - GTM и Facebook Pixel (ID из `runtimeConfig.public`), PageView при SPA-переходах;
- perf monitor plugin - только в dev: собирает клиентские метрики производительности, когда монитор включен.

Плагин нужен там, где поведение должно жить на уровне всего приложения, а не внутри конкретной страницы.

### 2.8. Store / клиентское состояние

Роль: хранить состояние, которое принадлежит пользовательской сессии.

Папка:

```text
app/stores/
```

Сейчас основной store - корзина.

Корзина хранит:

- компактные позиции (`toCartItem`): ID, вариация, выбранные атрибуты (`attributes` для показа, `variation` со слагами для заказа), количество, название, путь, картинка, цена на момент добавления — без галереи, похожих товаров и отзывов. Позиция определяется `cartLineKey`: вариация + слаги, поэтому одна вариация с «любым» цветом в двух цветах — две позиции;
- примененный купон;
- предварительную сумму (итог все равно считает WP через `api/cart/quote`).

Данные корзины дополнительно сохраняются в `localStorage`, чтобы пользователь не потерял корзину после перезагрузки страницы. Это именно клиентское состояние, а не основной источник товаров.

Геттеры store читают только его состояние, а в `localStorage` заглядывает только `hydrate()`, который вызывается после гидрации. Если читать `localStorage` во время гидрации, клиентская разметка разойдется с серверной, где корзина пустая, а в production Vue такие расхождения атрибутов (например, `disabled` у кнопки) не исправляет.

Правило: store стоит использовать для данных, которые меняются на клиенте и нужны в разных частях интерфейса. Контент, меню, SEO и каталог лучше не хранить в глобальном store без необходимости, потому что они приходят из backend и зависят от маршрута, языка и query-параметров.

### 2.9. Assets и стили

Папка:

```text
app/assets/
```

Структура стилей разделена по смыслу:

- `base` - reset, normalize, базовая сетка, шрифты;
- `utility` - переменные, типографика, контейнеры, media queries, кнопки;
- `components` - стили маленьких компонентов;
- `layout` - стили крупных layout-блоков;
- `page` - стили конкретных страниц;
- `vendor` - стили сторонних библиотек.

Главная точка подключения стилей:

```text
app/assets/scss/main.scss
```

Также проект использует локальные шрифты, изображения и SVG-спрайт через общий компонент иконок.

## 3. Зависимости

Текущий проект использует следующие основные зависимости:

- `nuxt` - приложение, маршрутизация, SSR/гидрация, server API;
- `@nuxtjs/i18n` - локализация маршрутов и интерфейсных переводов;
- `pinia` и `@pinia/nuxt` - глобальное клиентское состояние;
- `@vuelidate/core` и `@vuelidate/validators` - валидация форм;
- `swiper` - слайдеры, карусели и lightbox-навигация;
- `vue-select` - кастомные select-поля, например выбор размера или фильтра;
- `sass-embedded` - сборка SCSS;
- `typescript` и `vue-tsc` - типизация и проверка Vue/TypeScript-кода.

При переносе на другой фреймворк важно повторить не эти конкретные пакеты, а их роли:

- фреймворк с маршрутизацией и серверной прослойкой;
- i18n-решение;
- клиентский store;
- валидатор форм;
- библиотека слайдеров;
- пагинация ссылками `?page=N` (свой `UiCPagination`: роботы должны видеть `<a href>`, а не кнопки);
- компонент select;
- SCSS/PostCSS/CSS pipeline;
- инструмент проверки типов.

## 4. Конфигурация

Главный конфиг:

```text
nuxt.config.ts
```

В нем описаны:

- модули приложения;
- i18n-локали;
- базовый WordPress URL;
- runtime config;
- глобальные стили;
- Vite-настройки;
- server route cache rules;
- базовые head-теги;
- оптимизация public assets.

Настройки окружения задаются переменными `NUXT_*` (полный список с комментариями — `.env.example`):

| Переменная | Назначение |
|---|---|
| `NUXT_WP_SITE_URL` | адрес WordPress для BFF (локально `http://branded.loc`, на VPS — внутренний адрес). Старое имя `WP_SITE_URL` читается как значение по умолчанию при сборке |
| `NUXT_WP_TIMEOUT` | таймаут запроса к WP, мс |
| `NUXT_PUBLIC_SITE_URL` | домен сайта для canonical, hreflang, og:url |
| `NUXT_BFF_SECRET` | = `BRANDED_BFF_SECRET` в `wp-config.php` |
| `NUXT_REVALIDATE_SECRET` | = `BRANDED_REVALIDATE_SECRET` в `wp-config.php` |
| `NUXT_PUBLIC_GTM_ID`, `NUXT_PUBLIC_FB_PIXEL_ID` | аналитика, только на проде |

Это правильная практика: окружение может меняться между local/stage/production, но код приложения не должен зависеть от конкретного домена.

i18n настроен с `trailingSlash: true` (URL как в WordPress: `/uk/`, `/cart/`) и без `detectBrowserLanguage`: Google не советует редирект по языку браузера, а при кеше HTML такой редирект закешировался бы.

## 5. Как хранятся и читаются данные

### 5.1. Постоянные данные

Постоянные данные хранятся на backend:

- товары;
- категории;
- страницы;
- меню;
- переводы URL;
- SEO;
- отзывы;
- заказы.

Frontend читает их через локальные endpoint-ы в `server/api/`.

### 5.2. Данные страницы

Для каждой страницы создается ключ загрузки, который обычно зависит от:

- типа страницы;
- текущего URL или slug;
- языка;
- номера страницы;
- query-параметров фильтров или сортировки.

Это позволяет корректно разделять кеш и не смешивать данные разных языков, страниц и фильтров.

### 5.3. Клиентские данные

На клиенте хранятся только данные пользовательской сессии:

- корзина;
- состояние попапов;
- состояние loader-а переключения языка;
- опциональные метрики производительности;
- временное состояние форм и фильтров.

Корзина и perf monitor используют `localStorage`, потому что эти данные должны переживать перезагрузку страницы. Попапы и loader хранятся в реактивном состоянии приложения, потому что они нужны только во время текущей сессии.

### 5.4. Кеширование

Кеширование включается только в production-сборке (хук `nitro:config` в `nuxt.config.ts`): в dev кеш Nitro лежит на диске (`.nuxt/cache`), переживает перезапуск и после смены адреса WP или правки в админке отдавал бы старые ответы. В production кеш настроен для GET-endpoint-ов BFF: `route`, `menus`, `archive/*`, `product/get_single_product`, `home`, `page`, `reviews`, `search` (от 2 минут до часа, с отдачей устаревшего ответа на время обновления). Ключ кеша включает query.

Правило кеша нельзя вешать на префикс, под которым есть POST: кешированный обработчик Nitro не передает тело и заголовки запроса. Поэтому для товара правило стоит на `/api/product/get_single_product`, а не на `/api/product/**` (там же `POST /api/product/review`).

Когда в WP что-то меняется, он вызывает `POST /api/_revalidate {scopes}` с секретом, и endpoint удаляет записи кеша этих разделов (`catalog`, `seo`, `menu`, `home`).

Это снижает количество обращений к backend, но не делает frontend владельцем данных. Источник истины остается на WordPress/WooCommerce.

## 6. Модуль локализации и переключения языка

Локализация состоит из трех частей:

1. Локализованные маршруты.
2. Интерфейсные переводы.
3. Контент и URL, которые приходят из backend.

### 6.1. Локали

В проекте используются две локали:

- `ru` - язык по умолчанию;
- `uk` - дополнительный язык.

Стратегия маршрутов:

```text
prefix_except_default
```

Это значит:

- язык по умолчанию открывается без префикса;
- остальные языки получают префикс в URL.

Пример идеи:

```text
/product/example/
/uk/product/example/
```

Слаги в языках часто разные (`/brand/flex/` ↔ `/uk/brand/flex-uk/`), поэтому путь перевода нельзя получить заменой префикса: его отдает WP в `alternates`.

Интерфейсные переводы хранятся в JSON-файлах:

```text
i18n/locales/ru.json
i18n/locales/uk.json
```

Эти файлы подходят для коротких интерфейсных строк: кнопки, подписи, состояния, общие сообщения.

### 6.2. Контентные переводы

Контентные данные не зашиты во frontend. Для страниц, товаров, меню, SEO и breadcrumbs frontend передает текущий язык в запросах:

```text
lang=ru
lang=uk
```

Backend возвращает данные уже на нужном языке. Такой подход особенно важен для CMS и магазина, потому что переводы товаров, категорий, описаний и SEO должны управляться из админки.

### 6.3. Переводы текущей страницы

Отдельного запроса языков нет. Переводы страницы приходят в `alternates` из того же `api/route`, что и SEO. Из них строятся:

- `<link rel="alternate" hreflang="ru|uk|x-default">` в `<head>` (кроме `?page=N`, как в WP);
- ссылки переключателя языка.

`usePageSeo` кладет `alternates` в словарь `usePageAlternates()` по пути страницы. Шапка берет переводы по своему текущему пути. Словарь, а не одно значение, нужен затем, чтобы при клиентском переходе уходящая страница не перетирала данные новой. Если перевода нет, ссылка ведет на главную этого языка. Для маршрутов фронта (корзина, поиск) меняется только префикс (`switchLocalePath`).

### 6.4. UI переключателя

Компонент переключателя языка получает готовый список `{ code, path }` и рисует ссылки (`<NuxtLink>`), а не кнопки. В шапке он обернут в `<ClientOnly>`: шапка рендерится на сервере раньше страницы, поэтому переводы на этот момент еще неизвестны. Роботы получают переводы из hreflang.

### 6.5. Навигация при переключении

Клик по ссылке языка включает loader, затем происходит обычная навигация.

Loader выключается глобальным plugin-ом после:

- успешного завершения страницы;
- ошибки приложения;
- ошибки router-а.

Это защищает интерфейс от состояния, когда пользователь нажал смену языка, началась загрузка, но навигация завершилась ошибкой или была прервана.

### 6.6. Правило для переноса

Чтобы повторить этот модуль в другом фреймворке, нужно сохранить такие границы:

- язык должен быть частью маршрута;
- короткие UI-строки должны храниться в локальных словарях;
- контент должен приходить с backend по параметру языка;
- backend должен уметь отдавать альтернативные URL для текущей страницы;
- переключатель языка должен быть простым UI-компонентом;
- реальная навигация и loader должны управляться на уровне layout/router.

## 7. Модуль меню

Header, mobile и footer menu приходят одним запросом `GET /api/menus?lang=` (`useMenus`). Шапка и подвал используют общий ключ `menus:{lang}`, поэтому запрос один на язык. Ссылки верстки на конкретные WP-страницы (помощь, «Sales», блоки главной) берутся из `useSiteLink()`, где для каждого языка указан свой путь.

Компонент меню отвечает только за отображение вложенной структуры. Сама структура меню приходит с backend, поэтому ее можно менять из CMS без изменения frontend-кода.

Переносимый принцип: меню должно быть data-driven. Frontend должен уметь рисовать вложенную структуру, но не должен жестко хранить дерево меню в коде.

## 8. Модуль каталога, фильтров и пагинации

Каталог строится вокруг URL и query-параметров.

Все архивы рисует `LayoutLArchivePage`. Товары запрашиваются одним параметром `url` (`route.fullPath`): по пути WP определяет таксономию и термин (`/product-category/`, `/brand/`, `/sezon/`, `/бренд/`…), из query берет `page`, сортировку и фильтры по атрибутам. Чужие параметры (`utm_*`, `gclid`) WP игнорирует. Параллельно с товарами грузятся `api/route` (SEO, крошки, переводы) и сайдбар. Распродажа — тот же компонент с `on_sale`.

Ключ загрузки товаров зависит от `route.fullPath`, поэтому смена фильтра или страницы — это просто `router.push({ query })`, и товары перезапрашиваются сами. Фильтры грузятся отдельным блоком по таксономии архива.

Пагинация (`UiCPagination`) — ссылки `?page=N`. Старые адреса WP `/page/N/` дают 301 на `?page=N`. На `?page=N` canonical указывает на саму страницу, есть `rel=prev/next`, hreflang не выводится — как на живом WP. Пагинация в URL важна для:

- возможности поделиться ссылкой;
- SEO;
- корректной работы кнопок назад/вперед;
- предсказуемого восстановления состояния.

Переносимый принцип: состояние каталога должно жить в URL, а не только во внутреннем состоянии компонента.

## 9. Модуль товара

Страница товара загружает параллельно `api/route` и товар. В ответе товара уже есть похожие товары и отзывы, поэтому они попадают в SSR-HTML.

Товарная страница отвечает за:

- отображение основной информации; характеристики берутся из структурированных `specs` с подписями из i18n;
- картинки как в теме WP: `<a href="оригинал">` + `<picture>` с `single_xl` (840×1080) для широких экранов и `archive_xl` для узких, alt из медиатеки, preload главного фото;
- до 991px фото листаются слайдером Swiper (как `initProductGallerySlider` в теме: точки, автопрокрутка, free mode от 576px), шире слайдер уничтожается и остаётся главное фото + сетка галереи; включение по `matchMedia`, фото растягиваются на ширину колонки, как в теме;
- выбор вариации по `variation_attributes` / `variations` (`useProductVariation`): атрибут типа `color` — квадратики цвета, остальные — `vue-select`; недоступные сочетания приглушены, выбор несовместимого варианта переключает остальные атрибуты на вариацию в наличии; бренд и другие атрибуты с одним вариантом не показываются. Если WP не отдал `variation_attributes` (простой товар), остаётся прежний выбор размера из `size_attribute`;
- добавление в корзину;
- открытие быстрого заказа с выбранной вариацией;
- отзывы и форму нового отзыва (`POST /api/product/review`);
- открытие lightbox для изображений и видео;
- GA4-события `view_item` и `add_to_cart`.

Добавление в корзину не обращается сразу к backend. Оно обновляет клиентский store корзины. Backend подключается позже, когда пользователь оформляет заказ.

Переносимый принцип: страница товара должна разделять публичные данные товара и пользовательское действие. Данные товара приходят из backend, а выбор пользователя живет в клиентском состоянии до checkout.

## 10. Модуль корзины и заказа

Корзина хранится в клиентском store и дублируется в `localStorage`.

Корзина используется в:

- header;
- mini-cart;
- странице корзины;
- checkout;
- странице успешного заказа.

Корзина и checkout при открытии и при каждом изменении корзины запрашивают `POST /api/cart/quote`: WP пересчитывает цены по базе, проверяет наличие и купон. Суммы и ошибки позиций («нет в наличии») показываются из котировки. Купон, который WP не принял, из корзины убирается.

Checkout:

- читает товары из store;
- валидирует форму (`useOrderForm`, общие правила в `utils/validation.ts`);
- отправляет заказ с `payment_method`, принятым купоном и `lang`;
- показывает ошибки WP: 422 по полям и товарам, 429 при лимите заказов;
- из ответа (URL `…/order-received/{id}/?key=wc_order_…`) берет номер и ключ, очищает корзину и переводит пользователя на страницу успешного заказа.

Страница успешного заказа:

- получает данные заказа по номеру **и ключу** (без ключа WP отвечает 404: данные покупателя не должны открываться перебором номеров);
- показывает сводку;
- отправляет GA4 `purchase` один раз на заказ.

«Купить в 1 клик» использует ту же форму, но отправляет один товар с выбранной вариацией и корзину не трогает.

Выбранные атрибуты уходят в WP как `products[].variation` (слаги). WP берет из них только значения для атрибутов вариации «любое» и записывает их в мету позиции заказа, как корзина WooCommerce. Корзина показывает атрибуты из котировки (на языке страницы), страница заказа — `attributes` позиции.

Переносимый принцип: до оформления заказа корзина может быть клиентской. После отправки формы источником истины становится backend-заказ.

## 11. Модуль поиска

Поиск состоит из двух сценариев:

- быстрый поиск в header;
- полноценная страница результатов.

Быстрый поиск:

- реагирует на ввод от трех символов;
- использует задержку перед запросом;
- показывает короткий список товаров;
- не блокирует основную навигацию.

Страница поиска:

- читает запрос из URL (`/search/?s=`; старый адрес WP `/?s=` дает 301 сюда);
- загружает результаты с учетом языка (GET, кешируется);
- поддерживает пагинацию;
- показывает пустое состояние;
- закрыта от индексации (`noindex, follow`), но ссылки на товары роботы проходят.

Переносимый принцип: поисковый запрос должен быть частью URL, а быстрый поиск должен быть только UX-ускорением, не заменяющим полноценную страницу результатов.

## 12. SEO и breadcrumbs

SEO, крошки и переводы страницы приходят одним ответом `api/route`, который WP собирает через Yoast (тот же title, description, robots, canonical и граф schema, что в HTML темы). `usePageSeo` выводит их как есть, а хост canonical, og:url и hreflang приводит к `siteUrl`.

Breadcrumbs — те же крошки Yoast (по основной категории товара). Компонент только отображает список.

Статусы и редиректы:

- 404 только если WP ответил 404; любой сбой WP дает 503 с `noindex`, чтобы страницы не выпадали из индекса;
- `redirect` из `api/route` (слаг другого языка, лишние родители категории, `/shop/`) дает 301 с сохранением query;
- слеш в конце, `/page/N/` и `/?s=` обрабатывает серверный middleware.

`public/robots.txt` повторяет правила живого сайта, карты сайта Yoast проксируются. Служебные страницы (корзина, checkout, заказ, поиск) получают `X-Robots-Tag` из `routeRules` и `<meta name="robots">`.

Переносимый принцип: SEO и breadcrumbs лучше считать данными страницы, а не частью визуального компонента.

## 13. Попапы и модальные окна

Попапы управляются через общий popup state.

Модуль умеет:

- открыть попап по имени;
- передать в него данные;
- закрыть текущий попап;
- закрыть все попапы;
- поддерживать уровни, если нужно несколько слоев.

Глобальный plugin закрывает попапы при смене маршрута. Исключения можно делать для сценариев, где изменение URL не должно закрывать попап, например мобильные фильтры.

Переносимый принцип: модальные окна лучше централизовать. Компоненты должны не импортировать конкретный popup напрямую, а вызывать общий метод открытия с именем и payload.

## 14. Формы и валидация

Формы checkout и быстрого заказа используют общий `useOrderForm` и общие правила `utils/validation.ts` (телефон 10–15 цифр, как проверяет WP, нормализуется при вводе). Формы отзыва и подписки устроены так же, но проще.

Общий подход:

- состояние формы хранится локально в компоненте формы;
- правила валидации отделены от разметки;
- отправка защищена от повторного запроса;
- при успехе данные передаются в backend через server API;
- ошибки сервера (422 с кодами полей) показываются у полей, тексты берутся из i18n по коду;
- в каждой форме есть скрытое поле-ловушка `website` для ботов;
- при ошибке интерфейс остается управляемым, без потери введенных данных.

У поля телефона нет `maxlength`: вставленный номер `+38 (050) 123-45-67` браузер обрезал бы до нормализации.

Переносимый принцип: форма должна иметь три отдельных слоя - состояние, валидацию и отправку.

## 15. Loader-ы и состояния запросов

В проекте есть несколько уровней загрузки:

- page loader для загрузки страницы;
- spinner внутри отдельных блоков;
- loader при переключении языка;
- флаг запроса для форм и действий.

Это важно, потому что не каждая загрузка должна блокировать весь сайт. Например, фильтры могут показывать локальный spinner, а смена языка может показывать общий page loader.

Переносимый принцип: loader должен соответствовать масштабу действия.

## 16. Монитор производительности

В проекте есть клиентский perf monitor.

Он собирает:

- метрики первой загрузки;
- метрики клиентских переходов;
- длительность запросов;
- количество запросов на навигацию;
- тип маршрута.

Монитор работает только в dev (в production-сборке плагин сразу выходит), включается через query-параметр и хранит данные в `localStorage`. Это вспомогательный diagnostic-модуль, который не участвует в бизнес-логике магазина.

Переносимый принцип: диагностику лучше держать отдельным модулем, чтобы ее можно было включать и выключать без влияния на основные сценарии.

## 16a. Аналитика

GTM и Facebook Pixel подключает `plugins/analytics.ts`, как `base.twig` темы. ID задаются только на проде, без них плагин ничего не делает. GA4-события `view_item`, `add_to_cart`, `view_item_list`, `select_item`, `purchase` и `view_search_results` уходят в dataLayer в формате темы WP (`useAnalytics`), поэтому существующие теги GTM продолжают работать. При SPA-переходах уходят `fbq('track', 'PageView')` и событие `virtual_page_view` в dataLayer. Для тегов просмотра страницы в GTM нужен триггер на это событие или «History Change».

## 17. Рекомендуемая структура для повторения

Если переносить проект на другой фреймворк, можно использовать такую структуру:

```text
src/
  app/
    routes/
    layouts/
    pages/
  api/
    backendClient
    modules/
      route
      menus
      archive
      cart
      home
      page
      product
      reviews
      search
      subscribe
      revalidate
  components/
    ui/
    layout/
    forms/
    popups/
  services/
    seo
    i18n
    popup
    requests
    perf
  store/
    cart
  i18n/
    locales/
  assets/
    styles/
    fonts/
    images/
```

Главное - сохранить границы ответственности:

- routes/pages собирают данные;
- api layer общается с backend;
- services/composables держат повторяемую логику;
- layout components собирают крупные блоки;
- ui components остаются маленькими и переиспользуемыми;
- store хранит только клиентскую сессию;
- backend остается источником бизнес-данных.

## 18. Правила добавления нового модуля

При добавлении нового раздела сайта лучше идти по такому порядку:

1. Определить, где источник данных.
2. Добавить backend endpoint или убедиться, что он уже есть.
3. Добавить локальный server/api endpoint как адаптер.
4. Создать страницу, которая загружает данные по URL, языку и query-параметрам.
5. Вынести крупные блоки в layout-компоненты.
6. Переиспользуемые элементы вынести в ui-компоненты.
7. Если есть повторяемая логика, вынести ее в service/composable.
8. Если есть клиентское состояние между страницами, добавить store.
9. Добавить SEO и breadcrumbs: `useRouteData` + `guardPageRoute` + `usePageSeo` для страниц из WP, `useServicePageHead` для служебных.
10. Проверить поведение при смене языка (переводы слагов, hreflang).
11. Проверить loading/error/empty states, включая 503 при недоступном WP.
12. Тексты интерфейса — только через `i18n/locales/*.json`, в обоих языках.
13. Если endpoint кешируется в `routeRules`, убедиться, что под тем же префиксом нет POST.

## 19. Короткая архитектурная формула

Проект можно описать так:

```text
WordPress/WooCommerce хранит данные.
Server API frontend-приложения адаптирует эти данные.
Страницы загружают данные по маршруту и языку.
Layout-компоненты собирают большие секции.
UI-компоненты отображают маленькие элементы.
Composables/plugins управляют общим поведением.
Store хранит только клиентскую сессию.
i18n связывает маршруты, словари и контент backend.
```

Именно эту формулу стоит сохранять при переносе проекта на другой стек.
