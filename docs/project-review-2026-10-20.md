# Ревью проекта branded.com.ua: Nuxt 4 + headless WordPress

Дата: 20.10.2026. Прошлая оценка и план работ лежат в `C:\Users\sasha\.claude\plans\composed-seeking-crescent.md` (дальше «прошлый план»). Этот документ — новый срез: что стало лучше, что осталось и какой долг накопился.

## Коротко

- **Подход выбран верно.** Nuxt-фронт ходит в WordPress через свой серверный слой (BFF), SEO берётся из Yoast, языки из WPML, магазин остаётся на WooCommerce. Редакторы работают как раньше, а фронт можно ускорять кешем.
- **Код стал заметно лучше.** Почти все блокеры прошлого ревью закрыты: дыры в API, SEO-паритет, корректность каталога и заказов, i18n, аналитика. Готовность выросла примерно с 35–40% до **60–65%**.
- **Главный риск теперь не в коде, а в процессе.** В обоих репозиториях ничего не закоммичено, хотя часть кода темы уже работает на проде. CI, тестов, линтера и staging нет. `ARCHITECTURE_GUIDE.md` никогда не был в git: 20.10 его не оказалось в проекте, 21.10 он снова лежит в корне.
- **Инфраструктуры под запуск пока нет.** Кеш Nitro хранится в памяти процесса. На живом WP нет постоянного object cache: каждый запрос к API отвечает 0,6–0,9 с.
- **До запуска:** примерно **14–18 рабочих дней**. После запуска ещё **13–20 дней** на поддерживаемость. Оценки грубые, ±30%.

## 3. Как устроено сейчас

```
Браузер
  │  SSR-HTML, затем SPA-переходы
  ▼
Nuxt 4 (app/)  ── pages → LArchivePage / product / [...page] → composables (usePageRoute, useSeo, useCartQuote…)
  │  $fetch('/api/…')
  ▼
BFF Nitro (server/api/*) ── проверка входа (wpString/wpInt/wpLang) → wpFetch (таймаут, 404/4xx/503)
  │  кеш Nitro на GET (routeRules в хуке nitro:config), сброс через POST /api/_revalidate
  ▼
WordPress (тема news, inc/rest-api-*.php) ── WooCommerce, Yoast (Surfaces API), WPML, ACF
  │  при сохранении товара, термина или меню: wp_cache last_changed + вебхук в Nuxt
```

Корзина хранится в `localStorage`. Цены, наличие и купон перед оформлением пересчитывает WP (`cart/quote`), заказ создаёт `cart/create_order`.

## 4. Плюсы и минусы самого подхода (headless WP + Nuxt)

**Плюсы**
- **SEO и контент остаются в привычных инструментах.** Title, description, robots, schema и крошки приходят из Yoast, переводы из WPML. Редакторам не нужно переучиваться, а фронт не дублирует SEO-логику.
- **Фронт отделён от PHP-шаблонов.** Вёрстку, маршруты и производительность можно менять без риска для админки и заказов.
- **Есть потенциал скорости.** С кешем BFF и HTML ответы могут отдаваться за десятки миллисекунд, хотя сам WP отвечает 0,6–0,9 с.
- **Меньше поверхность атаки.** Браузер не видит WP напрямую, секреты остаются на сервере. После переезда админку можно спрятать на `cms.`-поддомен.
- **Откат дешёвый.** Контракт API менялся аддитивно, поэтому тема WP продолжает работать как фронт и остаётся запасным вариантом.

**Минусы (цена подхода)**
- **Две системы в эксплуатации.** Node и PHP, два деплоя, два кеша и инвалидация между ними. Ошибка в инвалидации видна покупателю как устаревшая цена или наличие.
- **Каждую функцию WooCommerce приходится переносить вручную.** Кабинет, платёжные шлюзы с callback, плагины с фронтовым выводом, предпросмотр черновиков — всё это нужно делать отдельно. Новый WC-плагин теперь означает работу в двух репозиториях.
- **Корзина живёт только на клиенте.** Нет серверной корзины, брошенных корзин и синхронизации между устройствами. Для текущих задач это нормально, но это решение надо держать в голове.
- **Скорость сайта целиком зависит от кеша.** Холодный SSR товара — это `api/route` и `get_single_product`, около 1 с. Без Redis и кеша HTML новый фронт быстрее живого сайта не станет.
- **API живёт внутри темы.** Пока это так, смена или обновление темы ломает фронт (M1 из прошлого плана).

**Вывод:** для магазина, которому важно сохранить индекс и процесс редакторов, подход оправдан. Но он требует дисциплины эксплуатации: git, CI, staging, мониторинга кеша. Её пока нет.

## 5. Что сделано хорошо

1. **Честные HTTP-статусы.** `server/utils/wpFetch.ts`: 404 от WP остаётся 404, ошибки 4xx уходят клиенту вместе с `data` (ошибки полей заказа 422), сбой сети и 5xx превращаются в 503. Сбой WP не выкинет страницы из индекса. Страницы проверяют результат через `guardPageRoute()` (`app/composables/usePageRoute.ts`).
2. **Один резолвер маршрута.** `api/route` отдаёт тип объекта, `canonical_path`, `redirect`, `alternates`, SEO и крошки. На нём держатся 301 со слага другого языка, hreflang и переключатель языка. Особые страницы определяются по ID, а не по слагу.
3. **Редиректы в одном месте.** `server/middleware/01.redirects.ts` обрабатывает слеш в конце, `/page/N/` → `?page=N`, `/?s=` и кабинет, не обращаясь к WP.
4. **Аккуратный `<head>`.** `app/composables/useSeo.ts`: хост canonical и hreflang приводится к `siteUrl`, на `?page=N` canonical указывает на саму страницу, `rel=prev/next`, `<` в JSON-LD экранируется. Служебные страницы закрыты `noindex` и в `<head>`, и заголовком `X-Robots-Tag`.
5. **Корректность заказа.** Цены всегда берутся из БД. До создания заказа проверяются поля (ответ 422 с кодами), количество, наличие и купон через `WC_Discounts`. Заказ создаётся в `pending`, статус меняется последним. Есть honeypot, rate limit и проверка IP клиента через секрет. Страница заказа открывается только по ключу, событие `purchase` уходит один раз.
6. **Гидрация без расхождений.** Корзина подхватывается после `onNuxtReady` (`app/plugins/cart.client.ts`), в `localStorage` лежит компактная позиция.
7. **Продуманная инвалидация кеша.** В WP `wp_cache_get_last_changed` плюс один вебхук за запрос. В Nuxt `timingSafeEqual` и очистка по scope.
8. **Комментарии объясняют «почему».** Например, почему POST нельзя класть под кешируемый префикс, или почему `maxlength` убран у телефона. Для небольшого проекта это редкость и большая ценность.
9. **Справочник API.** `docs/wp-api.md` (456 строк) описывает текущий контракт, ошибки, кеш и константы.
10. **Чистка дублирования.** Категории, бренды, сезоны и прочие таксономии собраны на общем `LArchivePage.vue`. Мёртвые прокси и `v-pagination-3` удалены.

## 6. Проблемы и риски

Уровни: **🔴 до запуска**, **🟠 желательно до запуска**, **🟡 после запуска**.

### 6.1 Процесс и управление изменениями

- 🔴 **G1. Ничего не закоммичено.**
  - Nuxt: после коммита `1e50fab update` изменены 75 файлов (+2137 / −2212) и около 40 новых файлов не отслеживаются.
  - Тема WP: изменены 15 файлов, `inc/rest-api-route.php` не отслеживается, при этом этот код **уже работает на проде**.
  - Нет точки отката и нет записи о том, что именно стоит на проде. Сбой диска или случайный `git checkout .` уничтожит всю работу двух фаз. Сообщения коммитов вида «update» не помогают искать изменения.
- 🔴 **G2. Документация вне git или устарела.** `ARCHITECTURE_GUIDE.md`, который по прошлому плану был «переписан под текущую схему», никогда не попадал в репозиторий. 20.10 его не было в проекте. 21.10 он нашёлся в корне, актуальный, и теперь закоммичен. `README.md` остался от Vue CLI (`npm run serve`, `npm run lint` — таких команд нет).
- 🔴 **G3. Нет CI и воспроизводимого деплоя.** Сборку, проверку типов и `php -l` никто не запускает автоматически. Тема выкатывается вручную, частями (сейчас на проде смесь двух фаз). Копирование файлов не удаляет на сервере то, что удалено локально: поэтому на проде до сих пор работает `inc/register.php` (проверено 21.10).
- 🟠 **G4. `.env` смотрит в прод** (`WP_SITE_URL` = боевой сайт). Любой заказ, отзыв или подписка из локального `nuxt dev` настоящие: письма клиенту и админу, Telegram, списание остатков. В `.env.example` это описано, но безопасным значением по умолчанию был бы `http://branded.loc` или staging.
- 🔴 **G5. Нет staging.** Сверку URL, Lighthouse, нагрузку и тестовые заказы негде проводить.

### 6.2 Производительность и кеш

- 🔴 **P-a. Кеш Nitro в памяти процесса.** В `nuxt.config.ts` нет `nitro.storage`, поэтому в production кеш хранится в памяти (драйвер `memory` из unstorage, без вытеснения). Последствия:
  - кеш пропадает при каждом рестарте или деплое;
  - в PM2 cluster (2 инстанса по плану) у каждого процесса свой кеш, и `POST /api/_revalidate` очищает только тот, на который попал вебхук. Второй ещё до 5 минут (меню — до часа) отдаёт старые цены и наличие;
  - память растёт без ограничения (см. P-b).

  → Redis (`nitro.storage.cache`, db1, как в плане) или хотя бы драйвер с LRU и лимитом.
- 🔴 **P-b. UTM-метки раздувают кеш.** `LArchivePage.vue:85-95` передаёт в BFF `url` = весь `route.fullPath`, а ключ кеша Nitro строится по полному пути с query. Каждый уникальный `gclid`, `fbclid` или `utm_*` даёт:
  - новую запись в памяти;
  - холодный запрос к WP (0,7–0,9 с на проде).

  Рекламный трафик, где `gclid` уникален у каждого клика, получает почти 0% попаданий в кеш. → В `server/api/archive/get_products.get.ts` оставлять в `url` только известные параметры: атрибуты-фильтры, `orderby`, `page`, `s`. Так же нормализовать ключ `useAsyncData`.
- 🟠 **P-c. HTML не кешируется** (SWR для страниц, P2 прошлого плана). При тёплом кеше API это терпимо, но TTFB < 200 мс из критериев запуска без кеша HTML не получить.
- 🟠 **P-d. WP без постоянного object cache** (P1 прошлого плана): на проде 0,6–0,9 с на любой запрос к API, повторный не быстрее. Решается Redis на VPS.
- 🟡 **P-e. Тяжёлые статические ассеты.**
  - Картинки главной лежат в бандле без оптимизации: `9130.jpg` 356 КБ, `product-row-bg.png` 270 КБ (фон 1920×990 в PNG), `bags1/2.jpg` 150–175 КБ.
  - Шрифты Montserrat не урезаны по наборам символов: 4 × ~90 КБ woff2.
  - В `app/assets/fonts` 19 МБ неиспользуемых eot/ttf/woff, плюс 3 неиспользуемые картинки (`dress1.jpg`, `dress2.jpg`, `accessory2.jpg`, ~376 КБ).
  - Нет `@nuxt/image` и WebP/AVIF.
  - SVG-спрайт (40 КБ) встроен в каждую страницу.
- 🟡 **P-f. Утечки в слайдерах.** В `LHeroHome`, `LProductRow`, `LBrand` и `LOutlet` экземпляры Swiper не уничтожаются при уходе со страницы. В `LRelated.vue:91-98` задан `autoplay`, но модуль `Autoplay` не подключён, поэтому автопрокрутка не работает.
- 🟡 **P-g. Лишний запрос в catch-all.** `app/pages/[...page].vue:76-79` для любого пути параллельно с `api/route` запрашивает `page/page`, в том числе для архивов таксономий (`/бренд/…`, `/color/…`). Каждый холодный рендер архива делает лишний запрос к WP, который отвечает 404.

### 6.3 Безопасность

- 🔴 **S-a. Уязвимые зависимости.** `npm audit --omit=dev`: 47 уязвимостей (6 critical, 27 high). Большинство в инструментах сборки (devtools, vite, tar, simple-git), но в рантайме тоже есть: `@vue/server-renderer` (XSS в именах атрибутов), `nitropack` (обход `routeRules` через percent-encoding), `devalue`, `defu`, `swiper` (prototype pollution, прямая зависимость). Доступна `nuxt` 4.4.8 (стоит 4.4.2). → Обновить и прогнать регрессию до запуска.
- 🟠 **S-b. Нет заголовков безопасности** (HSTS, CSP, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors`) ни в `routeRules`, ни в nginx (его пока нет).
- 🟠 **S-c. Лимиты запросов слабые.**
  - `server/api/subscribe.post.ts:8` хранит счётчики в `Map` в памяти. Записи не удаляются, у каждого инстанса свой счётчик.
  - IP берётся из первого значения `X-Forwarded-For`, которое подделывается, если nginx не перезаписывает заголовок (в плане это учтено).
  - В WP лимит на transients неатомарен.

  Для текущего масштаба терпимо, при переезде на Redis стоит перенести туда.
- 🟠 **S-d. Подписка шлёт письмо с купоном на любой адрес** (открытый вопрос прошлого плана). Нужен double opt-in. Кроме того:
  - обработчик `subscribe` в теме можно вызвать напрямую через `admin-ajax.php`, в обход лимита BFF;
  - купон один на всех и зашит в код (`Classes/NotificationSystem.class.php:51`).
- 🟡 **S-e. Состояние попапов на уровне модуля.** `app/composables/usePopup.ts:8` хранит его вне `useState`, поэтому на сервере оно общее для всех запросов. Сейчас попапы открываются только на клиенте, так что вреда нет, но это ловушка на будущее. В состоянии к тому же лежат функции (`onSelect`).
- 🟡 **S-f. `v-html` для контента WP** (описания, страницы, `price_html`, ACF-блоки). Граница доверия — учётные записи редакторов. Нужна 2FA для админов (есть в плане).

### 6.4 Качество кода Nuxt

- 🟠 **Q-a. Типы почти не используются.**
  - 58 из 60 `.vue` написаны на JS (`<script setup>` без `lang="ts"`), `app/types/wp-api.ts` (223 строки) используют только composables.
  - `nuxi typecheck` падает с 12 ошибками:
    - не хватает `@types/node`;
    - `usePopup`;
    - `tagPosition` в `plugins/analytics.ts`;
    - perf-monitor;
    - опция `api` у sass в `nuxt.config.ts`.
- 🟠 **Q-b. Нет линтера, форматтера и тестов.** Самая сложная логика без единого теста: выбор вариаций (`useProductVariation`), ключ позиции корзины, `normalizePath`, редиректы, `useSeo`. Основной риск регрессий здесь.
- 🟠 **Q-c. Контент и ID зашиты в код.**
  - Слаги WP-страниц в `useSiteLinks.ts`.
  - ID страниц 540, 27, 7318–7320 в `[...page].vue`.
  - Корневые категории 16/17/18 в `inc/rest-api-catalog.php:609`.
  - Ссылки баннеров на BeOm, телефон, email и соцсети в шаблонах.
  - Устаревшие маркетинговые тексты без i18n: «-20% for the entire summer collection 2023», «VeroS bags and accessories» (`LOutlet.vue`), «Ukrainian Underwear Essentials est. MMXX» (`LBrand.vue`), «15 брендов», кнопка «Присоединиться» с `href="#"` (`LBranded.vue`), «Sales» в меню.

  Если редактор сменит слаг, ссылка сломается без всякой ошибки.
- 🟠 **Q-d. Видимые мелкие баги (найдены по коду).**
